01

O que é — e o que não é

O scanner de verdade mora em outro repositório. Aqui está só a configuração de CI que o invoca, versionada e publicada como se fosse um pacote.

O scanner é uma imagem Docker publicada a partir de Tooark/base-images como {{SCANNER_IMAGE}}:{{SCANNER_VERSION}}. Dentro dela existe um CLI chamado ark-tools, que orquestra três ferramentas e produz um relatório JSON no formato {{REPORT_SCHEMA}} v{{REPORT_VERSION}}.

Este repositório resolve um problema diferente e bem específico:

O problema

“Temos 40 projetos. Não quero copiar 80 linhas de YAML de segurança em cada um deles, e quando o scanner mudar não quero editar 40 arquivos.”

Em vocabulário de desenvolvimento: este repositório é uma biblioteca, e os projetos que a consomem são os dependentes. A tag v{{COMPONENT_VERSION}} é a versão do pacote. Quem consome não copia código — declara uma dependência.

O pacote são os sete arquivos de templates/, um por scan: templates de CI/CD do GitLab que, incluídos em um pipeline, geram o job que roda o scan. O resto do repositório existe para que eles continuem fazendo o que a documentação diz.

E quem usa GitHub Actions?

Os mesmos scans existem para GitHub Actions, no repositório irmão Tooark/action-security-scanner, com os mesmos nomes de input em kebab-case. É por isso que cada input daqui que encaminha uma variável da imagem leva o nome dela em snake_case: TRIVY_SEVERITY é trivy_severity aqui e trivy-severity lá. Quem troca de plataforma não reaprende nada.

What it is — and what it is not

The scanner itself lives in another repository. What is here is only the CI configuration that invokes it, versioned and published as if it were a package.

The scanner is a Docker image built from Tooark/base-images and published as {{SCANNER_IMAGE}}:{{SCANNER_VERSION}}. Inside it there is a CLI called ark-tools that orchestrates three tools and produces a JSON report in the {{REPORT_SCHEMA}} v{{REPORT_VERSION}} format.

This repository solves a different and very specific problem:

The problem

“We have 40 projects. I do not want to copy 80 lines of security YAML into each of them, and when the scanner changes I do not want to edit 40 files.”

In development vocabulary: this repository is a library, and the projects that consume it are its dependents. The tag v{{COMPONENT_VERSION}} is the package version. Consumers do not copy code — they declare a dependency.

The package is the seven files in templates/, one per scan: GitLab CI/CD templates that, included in a pipeline, generate the job that runs the scan. The rest of the repository exists so they keep doing what the documentation says.

What about GitHub Actions?

The same scans ship for GitHub Actions from the sister repository Tooark/action-security-scanner, with the same input names in kebab-case. That is why every input here that forwards an image variable takes its name in snake_case: TRIVY_SEVERITY is trivy_severity here and trivy-severity there. Someone moving between the two platforms has nothing to relearn.

02

Os conceitos de CI, em termos de dev

Cinco termos destravam a leitura de qualquer arquivo deste repositório.

Termo O que é Analogia
Pipeline Tudo que roda quando você dá push A main() do build
Job Unidade isolada de trabalho, em um container ou VM limpa Uma função — roda em processo próprio
Stage Agrupamento sequencial de jobs (build → test → deploy) Fases. Jobs no mesmo stage rodam em paralelo
Runner A máquina que executa o job O servidor onde o processo roda
Artifact Arquivo que o job produz e que sobrevive ao fim dele Valor de retorno persistido

Dois detalhes explicam grande parte do código deste repositório.

Um job começa do zero toda vez

Container novo, disco vazio. É por isso que existe cache — sem ele, o Trivy baixaria um banco de vulnerabilidades de centenas de megabytes a cada execução. É por isso que cinco dos sete templates declaram um cache:.

Um job “falha” quando o comando sai com exit code diferente de zero

É assim que um scanner bloqueia um merge: ele encontra uma CVE crítica e retorna 1. Isso se chama failure gate, e boa parte dos inputs deste projeto existe só para você escolher quando o portão fecha.

Trivy

Falha quando uma severidade listada em trivy_severity_fail tem correção disponível.

desligar → trivy_exit_code: "0"

Hadolint

Falha a partir do nível definido em hadolint_failure_level.

desligar → hadolint_failure_level: "none"

Betterleaks

Falha quando qualquer segredo é detectado.

desligar → betterleaks_fail_on_findings: "false"

Existe um meio-termo: allow_failure: true mantém todos os gates, mas deixa o pipeline seguir — o job termina em alerta em vez de falha. Útil para adotar o scanner em um projeto legado sem travar todo mundo no primeiro dia.

CI concepts, in dev terms

Five terms unlock reading any file in this repository.

Term What it is Analogy
Pipeline Everything that runs when you push The build's main()
Job An isolated unit of work, in a fresh container or VM A function — runs in its own process
Stage A sequential grouping of jobs (build → test → deploy) Phases. Jobs in the same stage run in parallel
Runner The machine that executes the job The server the process runs on
Artifact A file the job produces that outlives it A persisted return value

Two details explain much of the code in this repository.

A job starts from nothing every time

New container, empty disk. That is why caching exists — without it Trivy would download a vulnerability database of hundreds of megabytes on every run. That is why five of the seven templates declare a cache:.

A job “fails” when the command exits non-zero

That is how a scanner blocks a merge: it finds a critical CVE and returns 1. This is called a failure gate, and much of this project's input surface exists only so you can choose when the gate closes.

Trivy

Fails when a severity listed in trivy_severity_fail has a fix available.

turn off → trivy_exit_code: "0"

Hadolint

Fails at or above the level set in hadolint_failure_level.

turn off → hadolint_failure_level: "none"

Betterleaks

Fails when any secret is detected.

turn off → betterleaks_fail_on_findings: "false"

There is a middle ground: allow_failure: true keeps every gate but lets the pipeline continue — the job ends in a warning instead of a failure. Useful for adopting the scanner in a legacy project without blocking everyone on day one.

05

Como um projeto consome um template

Um include: no .gitlab-ci.yml do projeto que quer ser escaneado. O mesmo arquivo tem dois endereços.

Include remoto

include:
  - remote: "https://raw.githubusercontent.com/Tooark/template-ci-security-scanner/v{{COMPONENT_VERSION}}/templates/full-scan.yml"
    inputs:
      stage: security
      image: "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA"
      trivy_severity: "CRITICAL,HIGH"

Aparece no pipeline um job chamado security:full-scan. Os inputs: são os argumentos da chamada, e são opcionais: sem nenhum, o job roda no stage test e pula a etapa de imagem. Funciona em qualquer instância que alcance raw.githubusercontent.com, a partir do GitLab 16.11.

Componente do catálogo

include:
  - component: $CI_SERVER_FQDN/tooark/ci-security-scanner/full-scan@{{COMPONENT_VERSION}}
    inputs:
      image: "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA"

Esta forma exige GitLab 17.0 e os templates publicados na própria instância (veja Catálogo e espelho). Atenção aos dois nomes: tooark/ci-security-scanner é o caminho que os exemplos assumem para o projeto-espelho na sua instância, não o repositório do GitHub. E às duas versões: o include remoto leva a tag, v{{COMPONENT_VERSION}}; o componente, a versão nua.

O job gerado é um job comum

Um include acrescenta um job ao pipeline de quem incluiu. O que os inputs não cobrem se muda redeclarando esse job pelo nome; o GitLab mescla as duas definições chave a chave: 

"security:full-scan":
  needs: ["build"]
  cache: []                # desliga o cache do Trivy
  variables:
    TRIVY_SCANNERS: "vuln,secret,misconfig,license"

A “escotilha de escape” do design; examples/remote-include.gitlab-ci.yml faz uso dela.

Para incluir o mesmo template duas vezes, dê ao segundo include outro job_name.

How a project consumes a template

One include: in the .gitlab-ci.yml of the project to be scanned. The same file has two addresses.

Remote include

include:
  - remote: "https://raw.githubusercontent.com/Tooark/template-ci-security-scanner/v{{COMPONENT_VERSION}}/templates/full-scan.yml"
    inputs:
      stage: security
      image: "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA"
      trivy_severity: "CRITICAL,HIGH"

A job named security:full-scan appears in the pipeline. The inputs: are the arguments of the call, and they are optional: with none, the job runs in the test stage and skips the image step. It works on any instance that can reach raw.githubusercontent.com, from GitLab 16.11 on.

Catalog component

include:
  - component: $CI_SERVER_FQDN/tooark/ci-security-scanner/full-scan@{{COMPONENT_VERSION}}
    inputs:
      image: "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA"

This form needs GitLab 17.0 and the templates published on the instance itself (see Catalog and mirror). Mind the two names: tooark/ci-security-scanner is the path the examples assume for the mirror project on your instance, not the GitHub repository. And the two versions: a remote include takes the tag, v{{COMPONENT_VERSION}}; a component, the bare version.

The generated job is an ordinary job

An include adds a job to the pipeline of whoever included it. What the inputs do not cover is changed by redeclaring that job by name; GitLab merges the two definitions key by key: 

"security:full-scan":
  needs: ["build"]
  cache: []                # disable the Trivy cache
  variables:
    TRIVY_SCANNERS: "vuln,secret,misconfig,license"

The design's escape hatch; examples/remote-include.gitlab-ci.yml makes use of it.

To include the same template twice, give the second include another job_name.

06

Anatomia de um template

Os sete arquivos têm a mesma forma: dois documentos YAML separados por ---. Em cima, os parâmetros; embaixo, o único job que eles preenchem. 

spec:
  inputs:
    trivy_severity:
      default: ""
      regex: "^[A-Z,]*$"
      description: "..."
---
"$[[ inputs.job_name ]]":
  stage: $[[ inputs.stage ]]
  image:
    name: "$[[ inputs.scanner_image ]]:$[[ inputs.scanner_version ]]"
    entrypoint: [""]
  tags: $[[ inputs.tags ]]
  timeout: $[[ inputs.timeout ]]
  allow_failure: $[[ inputs.allow_failure ]]
  rules: $[[ inputs.rules ]]
  cache: ...
  variables: ...
  before_script: ...
  script: ...
  artifacts: ...

spec: inputs — a assinatura

É a assinatura de função pública da biblioteca: o contrato com quem consome, e mudá-la quebra gente. Um template declara de 18 a 40 inputs, e só um é obrigatório: o image do image-scan. type:, options: e regex: restringem o valor, e o GitLab confere antes de o pipeline existir.

O job — direto dos inputs

O GitLab substitui cada $[[ inputs.x ]] quando o pipeline é criado. Um valor YAML que é exatamente um desses blocos mantém o tipo do input — é assim que tags e rules viram listas e allow_failure, booleano; dentro de uma string maior, como em image: name:, ele é escrito como texto. O cache: só existe nos cinco templates que usam o Trivy.

variables: — os inputs viram ambiente

  variables:
    ARK_IN_IMAGE: "$[[ inputs.image ]]"
    ARK_IN_SBOM: "$[[ inputs.sbom ]]"
    ARK_IN_TRIVY_SEVERITY: "$[[ inputs.trivy_severity ]]"

Todo input que o script lê fica no ambiente como ARK_IN_*; nenhum $[[ inputs.x ]] aparece dentro de before_script ou script.

Por quê

Colado direto no texto do script, um valor como "; rm -rf / # viraria comando. Como variável, ele é sempre apenas um valor — o raciocínio de prepared statements contra SQL injection.

Um booleano posto ali, como ARK_IN_SBOM, chega ao job como o texto true ou false. O GitLab aceita isso a partir da 16.11 — o que, junto com os inputs do tipo array, define a versão mínima.

before_script — exportar só o que não está vazio

ark_apply_inputs() {
  for _name in "$@"; do
    eval "_value=\${ARK_IN_${_name}:-}"
    if [ -n "${_value}" ]; then      # ← o coração da precedência
      export "${_name}=${_value}"
      echo "  ${_name}=${_value}"
    fi
  done
}

Para cada nome que recebe, a função lê ARK_IN_<NOME> e, se não estiver vazio, exporta <NOME> — o nome que a imagem lê. O eval só percorre a lista fixa de nomes que o template passa; nenhum input chega até ele.

script e artifacts — a linha de comando, e o que sobra dela 

set -- full-scan
if [ -n "${ARK_IN_IMAGE:-}" ]; then
  set -- "$@" "$ARK_IN_IMAGE"
fi
if [ "${ARK_IN_SBOM:-false}" = "true" ]; then
  set -- "$@" --sbom
fi
if [ -n "${ARK_IN_EXTRA_ARGS:-}" ]; then
  set -f
  set -- "$@" -- $ARK_IN_EXTRA_ARGS
  set +f
fi
ark-tools "$@"

set -- reescreve os argumentos posicionais do shell: é como se monta uma lista de argumentos em sh puro, que não tem arrays. Todo valor entra entre aspas, menos extra_args, dividido em palavras de propósito — sob set -f, para que um * não se expanda contra os arquivos do repositório.

O exit code do ark-tools é o resultado do job, e o artifacts: guarda os relatórios com when: always — o job que falha é justamente aquele cujo relatório alguém vai querer ler.

Anatomy of a template

All seven files have the same shape: two YAML documents separated by ---. Above, the parameters; below, the one job they fill in. 

spec:
  inputs:
    trivy_severity:
      default: ""
      regex: "^[A-Z,]*$"
      description: "..."
---
"$[[ inputs.job_name ]]":
  stage: $[[ inputs.stage ]]
  image:
    name: "$[[ inputs.scanner_image ]]:$[[ inputs.scanner_version ]]"
    entrypoint: [""]
  tags: $[[ inputs.tags ]]
  timeout: $[[ inputs.timeout ]]
  allow_failure: $[[ inputs.allow_failure ]]
  rules: $[[ inputs.rules ]]
  cache: ...
  variables: ...
  before_script: ...
  script: ...
  artifacts: ...

spec: inputs — the signature

It is the library's public function signature: the contract with consumers, and changing it breaks people. A template declares 18 to 40 inputs, and only one is required: image in image-scan. type:, options: and regex: constrain the value, and GitLab checks them before the pipeline exists.

The job — straight from the inputs

GitLab replaces every $[[ inputs.x ]] when the pipeline is created. A YAML value that is exactly one such block keeps the type of the input — that is how tags and rules become lists and allow_failure a boolean; inside a longer string, as in image: name:, it is written out as text. cache: only exists in the five templates that use Trivy.

variables: — inputs become environment

  variables:
    ARK_IN_IMAGE: "$[[ inputs.image ]]"
    ARK_IN_SBOM: "$[[ inputs.sbom ]]"
    ARK_IN_TRIVY_SEVERITY: "$[[ inputs.trivy_severity ]]"

Every input the script reads sits in the environment as an ARK_IN_*; no $[[ inputs.x ]] appears inside before_script or script.

Why

Pasted straight into the text of the script, a value like "; rm -rf / # would become a command. As a variable, it is always just a value — the reasoning of prepared statements against SQL injection.

A boolean placed there, such as ARK_IN_SBOM, reaches the job as the text true or false. GitLab accepts that from 16.11 on — which, together with array-typed inputs, sets the minimum version.

before_script — export only what is not empty

ark_apply_inputs() {
  for _name in "$@"; do
    eval "_value=\${ARK_IN_${_name}:-}"
    if [ -n "${_value}" ]; then      # ← the heart of the precedence rule
      export "${_name}=${_value}"
      echo "  ${_name}=${_value}"
    fi
  done
}

For each name it is given, the function reads ARK_IN_<NAME> and, if it is not empty, exports <NAME> — the name the image reads. The eval only walks the fixed list of names the template passes; no input reaches it.

script and artifacts — the command line, and what is left of it 

set -- full-scan
if [ -n "${ARK_IN_IMAGE:-}" ]; then
  set -- "$@" "$ARK_IN_IMAGE"
fi
if [ "${ARK_IN_SBOM:-false}" = "true" ]; then
  set -- "$@" --sbom
fi
if [ -n "${ARK_IN_EXTRA_ARGS:-}" ]; then
  set -f
  set -- "$@" -- $ARK_IN_EXTRA_ARGS
  set +f
fi
ark-tools "$@"

set -- rewrites the shell's positional arguments: it is how an argument list is built in plain sh, which has no arrays. Every value goes in quoted, except extra_args, split into words on purpose — under set -f, so that a * cannot expand against the files in the repository.

The exit code of ark-tools is the result of the job, and artifacts: keeps the reports with when: always — a failed job is precisely the one whose report someone will want to read.

07

O caminho de uma execução

Do include: ao relatório, na ordem em que as coisas acontecem.

  1. O projeto declara o include, com ou sem inputs.
  2. O GitLab cria o pipeline. Busca o arquivo, valida os inputs contra o spec: e substitui cada $[[ inputs.x ]]. Se a URL não responde ou um input não bate, o pipeline nem é criado.
  3. Um runner pega o job. Baixa {{SCANNER_IMAGE}}:{{SCANNER_VERSION}}, clona o repositório, restaura o cache ark-trivy-db e sobe o container com o entrypoint limpo. Daqui em diante tudo roda dentro da imagem do scanner.
  4. O before_script exporta os inputs não vazios, com os nomes que a imagem lê.
  5. O script chama o ark-tools, no mesmo shell: o runner junta os dois blocos em um script só. O exit code decide o job — diferente de zero é gate fechado.
  6. O runner guarda o que sobra. Os relatórios viram artifacts e o banco do Trivy volta para o cache, tenha o job passado ou não: os dois são declarados com when: always, porque um gate fechado falha o job de propósito.

A precedência, vista de dentro do job

input  >  variável de CI/CD  >  default da imagem

O job é o container do scanner; toda variável de CI/CD — do projeto, do grupo, do variables: do pipeline — já está no ambiente em que o ark-tools roda. O meio da regra não precisa de código: nada é encaminhado. O template só cuida das pontas: input com valor é exportado, e um export vence o que já estava no ambiente; input vazio não é, e a variável — ou o default da imagem — permanece.

É por isso que os inputs passam por ARK_IN_* em vez de irem direto para variables: TRIVY_SEVERITY: no GitLab, variável de projeto ou de grupo tem precedência sobre o variables: de um job, e o input perderia — a regra ao contrário.

Armadilha

Segredos vão pelo meio da regra: TRIVY_TOKEN, REPORT_TOKEN e credenciais de registry são variáveis de CI/CD mascaradas. Valores de input aparecem na configuração renderizada do pipeline, visível para quem tem acesso de leitura ao projeto. Um token passado como input é um token vazado.

Por que sete arquivos quase idênticos

Porque o spec: vale para o arquivo inteiro. Quem inclui image-scan.yml só pode passar o que o image-scan declara, e image é obrigatório só ali; um arquivo único, com um input para escolher o comando, aceitaria hadolint_config em um scan de imagem sem reclamar. Um arquivo por scan mantém exato o contrato de cada um, ao preço de repetir a estrutura — e duplicação sem verificação automática apodrece. É para isso que existem as verificações de Versão única.

The path of one run

From the include: to the report, in the order things happen.

  1. The project declares the include, with or without inputs.
  2. GitLab creates the pipeline. It fetches the file, validates the inputs against spec: and replaces every $[[ inputs.x ]]. If the URL does not answer or an input does not fit, the pipeline is never created.
  3. A runner picks the job up. It pulls {{SCANNER_IMAGE}}:{{SCANNER_VERSION}}, clones the repository, restores the ark-trivy-db cache and starts the container with its entrypoint cleared. From here on everything runs inside the scanner image.
  4. before_script exports the non-empty inputs, under the names the image reads.
  5. script calls ark-tools, in the same shell: the runner joins the two blocks into one script. The exit code decides the job — non-zero means a gate tripped.
  6. The runner keeps what is left. The reports become artifacts and the Trivy database goes back to the cache whether the job passed or not: both are declared with when: always, because a tripped gate fails the job on purpose.

The precedence rule, seen from inside the job

input  >  CI/CD variable  >  image default

The job is the scanner container; every CI/CD variable — from the project, the group, the pipeline's variables: — is already in the environment ark-tools runs in. The middle of the rule needs no code: nothing is forwarded. The template only looks after the ends: an input with a value is exported, and an export beats whatever was in the environment; an empty input is not, and the variable — or the image default — stands.

That is why inputs go through ARK_IN_* instead of straight into variables: TRIVY_SEVERITY: on GitLab, a project or group variable takes precedence over a job's variables:, and the input would lose — the rule backwards.

Trap

Secrets take the middle of the rule: TRIVY_TOKEN, REPORT_TOKEN and registry credentials are masked CI/CD variables. Input values appear in the rendered pipeline configuration, visible to anyone with read access to the project. A token passed as an input is a leaked token.

Why seven nearly identical files

Because a spec: applies to the whole file. Whoever includes image-scan.yml can only pass what image-scan declares, and image is required only there; a single file, with an input to pick the command, would accept hadolint_config on an image scan without complaint. One file per scan keeps each contract exact, at the price of repeating the structure — and duplication without automated verification rots. That is what the checks under Single source of truth are for.

Versão única e testes de contrato

A parte que mais ensina, e o padrão mais transferível deste repositório para qualquer outro projeto.

O problema

A mesma versão do scanner aparece em sete lugares: o default de scanner_version de cada template. Atualizar de {{SCANNER_VERSION}} para 2.0 e esquecer um deles significa um scan rodando versão antiga silenciosamente. YAML não tem compilador; ninguém percebe.

A solução

O VERSION é a constante única:

# Single source of truth for versions in this repository.
COMPONENT_VERSION={{COMPONENT_VERSION}}
SCANNER_IMAGE={{SCANNER_IMAGE}}
SCANNER_VERSION={{SCANNER_VERSION}}
REPORT_SCHEMA={{REPORT_SCHEMA}}
REPORT_VERSION={{REPORT_VERSION}}

Até este guia sai dele: as versões que você lê nesta página são preenchidas a partir do VERSION pelo scripts/render-docs.sh, no deploy.

E o scripts/check-sync.sh é o teste de contrato que falha o CI quando algo diverge. Ele verifica quatro invariantes:

  1. Todo template pina exatamente a imagem declarada em VERSION.
  2. Em cada template, todo ARK_IN_* declarado é de fato lido, e todo ARK_IN_* lido foi declarado.
  3. Todo input de um template está documentado nos dois READMEs.
  4. Toda referência de copiar e colar nos docs e nos exemplos pina COMPONENT_VERSION, e toda menção ao envelope do relatório cita REPORT_VERSION.
Por quê

O item 2 pega o bug mais chato deste tipo de projeto: você adiciona um input, documenta, e esquece de conectar uma das pontas. O usuário passa o valor, e nada acontece. Silenciosamente.

O que o GitLab só diria tarde demais

O GitLab só reporta um template quebrado quando um pipeline é criado — no projeto de quem consome, não neste. Três verificações fazem as mesmas perguntas antes:

  • scripts/validate-templates.py — o template está inteiro? Separador ---, todo $[[ inputs.x ]] declarado, todo input declarado em uso, default entre as options, exatamente um job.
  • scripts/check-examples.py — o GitLab aceitaria cada include documentado, em examples/ e nos READMEs? Input desconhecido, tipo errado, valor fora de options, input obrigatório faltando.
  • tests/templates.test.py — o job gerado faz a coisa certa? Renderiza cada template, roda o script dele contra um ark-tools de mentira e confere a linha de comando e o ambiente recebidos. Os dois últimos leem os templates pelo scripts/component.py.

A regra prática

Ao adicionar um input

Toque nos quatro lugares, ou as verificações vão te avisar: o spec:inputs do template, o bloco variables: como ARK_IN_*, o script do job que o lê, e as tabelas dos dois READMEs.

Para rodar as validações localmente, antes de abrir o PR:

python3 -m pip install pyyaml

python3 scripts/validate-templates.py
./scripts/check-sync.sh
python3 scripts/check-examples.py
python3 tests/templates.test.py
shellcheck -s bash scripts/*.sh

Single source of truth and contract tests

The part with the most to teach, and the most transferable pattern in this repository.

The problem

The same scanner version appears in seven places: the default of scanner_version in each template. Updating from {{SCANNER_VERSION}} to 2.0 and forgetting one of them means a scan silently running the old version. YAML has no compiler; nobody notices.

The solution

VERSION is the single constant:

# Single source of truth for versions in this repository.
COMPONENT_VERSION={{COMPONENT_VERSION}}
SCANNER_IMAGE={{SCANNER_IMAGE}}
SCANNER_VERSION={{SCANNER_VERSION}}
REPORT_SCHEMA={{REPORT_SCHEMA}}
REPORT_VERSION={{REPORT_VERSION}}

Even this guide comes out of it: the versions you read on this page are filled in from VERSION by scripts/render-docs.sh at deploy time.

And scripts/check-sync.sh is the contract test that fails CI when anything diverges. It checks four invariants:

  1. Every template pins exactly the image declared in VERSION.
  2. In each template, every declared ARK_IN_* is actually read, and every ARK_IN_* read was declared.
  3. Every input of a template is documented in both READMEs.
  4. Every copy-paste reference in the docs and the examples pins COMPONENT_VERSION, and every mention of the report envelope names REPORT_VERSION.
Why

Item 2 catches the nastiest bug in this kind of project: you add an input, document it, and forget to connect one of the ends. The user sets the value, and nothing happens. Silently.

What GitLab would only say too late

GitLab only reports a broken template when a pipeline is created — in a consumer's project, not in this one. Three checks ask the same questions ahead of time:

  • scripts/validate-templates.py — is the template whole? The --- separator, every $[[ inputs.x ]] declared, every declared input in use, default among the options, exactly one job.
  • scripts/check-examples.py — would GitLab accept every documented include, in examples/ and in the READMEs? Unknown input, wrong type, value outside options, missing required input.
  • tests/templates.test.py — does the generated job do the right thing? It renders each template, runs its script against a stand-in ark-tools and asserts on the command line and the environment it received. The last two read the templates through scripts/component.py.

The practical rule

When adding an input

Touch all four places, or the checks will tell you: the template's spec:inputs, its variables: block as ARK_IN_*, the job script that reads it, and the tables of both READMEs.

To run the validations locally, before opening the PR:

python3 -m pip install pyyaml

python3 scripts/validate-templates.py
./scripts/check-sync.sh
python3 scripts/check-examples.py
python3 tests/templates.test.py
shellcheck -s bash scripts/*.sh

O CI do próprio projeto

Uma dobra que confunde no começo: a pasta .github/workflows/ não tem nada a ver com o que o projeto entrega. É o CI deste repositório — que mora no GitHub, e por isso roda em GitHub Actions.

ci.yml — roda em push e pull request

Job lint: parseia todo YAML do repositório, roda as quatro verificações da seção anterior, passa o shellcheck (linter de shell) em scripts/ e no script de job de cada template — extraído pelos testes e lintado como sh, porque nada nele pode depender do shell que o runner escolher — e roda o actionlint (linter de GitHub Actions).

Job self-scan: como o repositório mora no GitHub, quem o escaneia é a Action irmã, Tooark/action-security-scanner — a mesma imagem e os mesmos comandos ark-tools dos templates daqui. Ela protege este repositório; quem testa os templates é o tests/templates.test.py.

Duas linhas valem atenção:

permissions:
  contents: read     # o token do job só lê — menor privilégio
uses: docker://rhysd/actionlint@sha256:b1934ee5...   # pinado por digest
Por quê

Uma tag Docker (:1.7.12) pode ser reapontada pelo dono da imagem a qualquer momento. Um digest SHA-256 é imutável. Como esse container de terceiro roda dentro do CI deste projeto, pinar por digest impede que código não revisado passe a rodar aqui sem nenhum commit.

release.yml — roda ao dar push em uma tag v*.*.*

Roda de novo as cinco validações locais, confere se a tag bate com COMPONENT_VERSION — tag v1.0.1 com VERSION=1.0.0 é release recusada —, cria o GitHub Release com notas geradas e move as tags flutuantes.

Referência Aponta para Quando usar

v{{COMPONENT_MINOR}} Último patch da linha {{COMPONENT_MINOR}} Patches automáticos
v{{COMPONENT_MAJOR}} Último release da linha {{COMPONENT_MAJOR}}.x Minors e patches automáticos
main Trabalho não lançado Nunca em um pipeline que te importa

dependabot.yml

Abre um PR semanal atualizando as Actions referenciadas, inclusive a Action irmã do self-scan. O comentário no arquivo fecha o raciocínio do digest: sem isso, pinar congelaria a dependência em vez de controlá-la. Pinar sem um mecanismo de atualização não é segurança, é dívida.

The project's own CI

A fold that confuses at first: the .github/workflows/ folder has nothing to do with what the project delivers. It is this repository's CI — which lives on GitHub, and therefore runs on GitHub Actions.

ci.yml — runs on push and pull request

Job lint: parses every YAML file in the repository, runs the four checks of the previous section, runs shellcheck (a shell linter) over scripts/ and over the job script of each template — dumped by the tests and linted as sh, because nothing in it may depend on the shell a runner picks — and runs actionlint (a GitHub Actions linter).

Job self-scan: since the repository lives on GitHub, what scans it is the sister Action, Tooark/action-security-scanner — the same image and the same ark-tools commands as the templates here. It guards this repository; what tests the templates is tests/templates.test.py.

Two lines are worth noticing:

permissions:
  contents: read     # the job token only reads — least privilege
uses: docker://rhysd/actionlint@sha256:b1934ee5...   # pinned by digest
Why

A Docker tag (:1.7.12) can be repointed by the image owner at any moment. A SHA-256 digest is immutable. Since that third-party container runs inside this project's CI, pinning by digest stops unreviewed code from starting to run here without a single commit.

release.yml — runs when a v*.*.* tag is pushed

Reruns the five local validations, checks that the tag agrees with COMPONENT_VERSION — tag v1.0.1 with VERSION=1.0.0 is a refused release — creates the GitHub Release with generated notes, and moves the floating tags.

Reference Resolves to Use when
v{{COMPONENT_VERSION}} Exactly that release Reproducible pipelines
v{{COMPONENT_MINOR}} Newest patch of the {{COMPONENT_MINOR}} line Automatic patch updates
v{{COMPONENT_MAJOR}} Newest release of the {{COMPONENT_MAJOR}}.x line Automatic minor and patch updates
main Unreleased work Never in a pipeline you care about

It is the Actions ecosystem convention — actions/checkout@v7 works this way. The README is honest about the cost: pinning v{{COMPONENT_MAJOR}} means running code you have not reviewed after the next release. A catalog component takes the same forms, without the v.

dependabot.yml

Opens a weekly PR updating the referenced Actions, including the sister Action of self-scan. The comment in the file closes the digest reasoning: without it, pinning would freeze the dependency instead of controlling it. Pinning without an update mechanism is not security, it is debt.

Decisões e armadilhas

As escolhas que parecem estranhas na primeira leitura, e o motivo de cada uma. Esta seção é a que mais economiza tempo quando algo dá errado.

A regra de precedência — o motivo dos default: "" 

input  >  variável de CI/CD  >  default da imagem

Input vazio nunca é encaminhado. Isso permite que um projeto, ou um grupo inteiro, defina TRIVY_SEVERITY uma vez como variável de CI/CD e deixe o input em branco em todos os includes, em vez de repetir. Definindo os dois, o input ganha.

Se o input vazio fosse encaminhado, ele sobrescreveria a variável com string vazia e quebraria esse padrão. É a diferença entre undefined e "".

O corolário já mordeu este projeto: um default não vazio é sempre encaminhado. dockerfiles e scan_mode tinham como default "Dockerfile" e "fs" — os mesmos da imagem, o que parecia inofensivo — e substituíam em silêncio um FULL_SCAN_DOCKERFILES ou FULL_SCAN_MODE definido como variável. Hoje os dois nascem vazios.

Booleanos e strings não são intercambiáveis

sbom: true, mas no_git: "true". Só allow_failure e sbom são boolean; os demais liga/desliga são strings entre aspas, e o GitLab recusa o include com o tipo trocado. Não é capricho: um input que encaminha uma variável precisa de um terceiro estado, “não definido”, e booleano não tem.

O cache do Trivy: uma chave fixa

O banco de CVEs do Trivy é grande. Baixá-lo a cada build é a parte mais lenta do scan e o jeito mais fácil de bater o rate limit do registry. Os templates que usam o Trivy cacheiam .cache/trivy sob a chave fixa ark-trivy-db, compartilhada por todos os branches.

Em instâncias self-hosted, por padrão o cache do runner fica no disco do próprio runner. Com vários runners, um job só acerta o cache se cair no runner que o escreveu. Configurar distributed caching (S3 ou equivalente) no config.toml é o que torna a taxa de acerto consistente.

entrypoint: [""] em todo template

A imagem tem um entrypoint que executa ark-tools direto. O GitLab Runner mantém o entrypoint da imagem e anexa um shell a ele. Sem limpar, o job morre antes do script rodar. Pelo mesmo motivo o executor precisa rodar o job dentro da imagem: shell e ssh não servem.

GIT_DEPTH: "0"

Por padrão, o GitLab faz shallow clone (só os commits mais recentes) porque é mais rápido. Mas o Betterleaks procura segredos no histórico — e o caso clássico é exatamente a chave commitada e “removida” depois.

Falha silenciosa

Com clone raso, o Betterleaks não vê quase nada e não reclama. O job passa verde e você acha que está protegido. Por isso os templates que leem o histórico forçam profundidade completa.

Uma imagem em registry privado precisa de credenciais

O image-scan e a etapa de imagem do full-scan puxam a imagem do registry por conta própria, e o registry do próprio projeto é privado a menos que o projeto seja público: o build empurra a imagem e o scan não consegue lê-la. A saída é redeclarar o job gerado com TRIVY_USERNAME: "$CI_REGISTRY_USER" e TRIVY_PASSWORD: "$CI_REGISTRY_PASSWORD" em variables:.

Relatórios podem conter os segredos que encontraram

Duas configurações transformam um artifact em vazamento: betterleaks_redact: "0" escreve os segredos detectados em texto claro, e adicionar secret a trivy_scanners coloca os achados do Trivy no relatório. Artifacts são baixáveis por qualquer um com acesso de leitura ao projeto. O default é redação de 100%, e o log imprime apenas regra, arquivo, linha e commit curto — nunca o segredo.

Duas pegadinhas menores

  • dockerfile-lint processa um arquivo por job. Para vários, use full-scan com dockerfiles: "a,b,c", ou inclua o template uma vez por arquivo com job_name diferente.
  • O default vazio de tags renderiza como tags: []. O GitLab não permite que um input omita uma palavra-chave, e lista vazia é como se diz “qualquer runner”. Pipelines aceitam; apenas o schema JSON do editor do GitLab reclama.

Decisions and traps

The choices that look strange on a first read, and the reason behind each. This is the section that saves the most time when something goes wrong.

The precedence rule — why default: "" everywhere 

input  >  CI/CD variable  >  image default

An empty input is never forwarded. That lets a project, or a whole group, set TRIVY_SEVERITY once as a CI/CD variable and leave the input blank in every include, instead of repeating it. Set both and the input wins.

If an empty input were forwarded, it would overwrite the variable with an empty string and break that pattern. It is the difference between undefined and "".

The corollary has already bitten this project: a non-empty default is always forwarded. dockerfiles and scan_mode used to default to "Dockerfile" and "fs" — the image's own defaults, which looked harmless — and silently replaced a FULL_SCAN_DOCKERFILES or FULL_SCAN_MODE set as a variable. Both now start out empty.

Booleans and strings are not interchangeable

sbom: true, but no_git: "true". Only allow_failure and sbom are boolean; the other on/off switches are quoted strings, and GitLab rejects an include with the types swapped. It is not a whim: an input that forwards a variable needs a third state, “not set”, and a boolean has none.

The Trivy cache: one fixed key

Trivy's CVE database is large. Downloading it on every build is the slowest part of a scan and the easiest way to hit a registry rate limit. The templates that use Trivy cache .cache/trivy under the fixed key ark-trivy-db, shared by every branch.

On self-hosted instances, by default the runner cache lives on the runner's own disk. With several runners, a job only hits the cache if it lands on the runner that wrote it. Configuring distributed caching (S3 or equivalent) in config.toml is what makes the hit rate consistent.

entrypoint: [""] in every template

The image has an entrypoint that execs ark-tools directly. GitLab Runner keeps the image entrypoint and attaches a shell to it. Without clearing it, the job dies before the script runs. For the same reason the executor has to run the job inside the image: shell and ssh will not do.

GIT_DEPTH: "0"

By default GitLab does a shallow clone (only the most recent commits) because it is faster. But Betterleaks looks for secrets in the history — and the classic case is exactly the key that was committed and “removed” afterwards.

Silent failure

With a shallow clone, Betterleaks sees almost nothing and does not complain. The job passes green and you believe you are protected. That is why the templates that read the history force full depth.

An image in a private registry needs credentials

image-scan and the image step of full-scan pull the image from the registry themselves, and the project's own registry is private unless the project is public: the build pushes the image and the scan cannot read it. The way out is to redeclare the generated job with TRIVY_USERNAME: "$CI_REGISTRY_USER" and TRIVY_PASSWORD: "$CI_REGISTRY_PASSWORD" under variables:.

Reports can contain the secrets they found

Two settings turn an artifact into a disclosure: betterleaks_redact: "0" writes detected secrets in cleartext, and adding secret to trivy_scanners puts Trivy's findings in the report. Artifacts are downloadable by anyone with read access to the project. The default is 100% redaction, and the log prints only rule, file, line and short commit — never the secret.

Two smaller gotchas

  • dockerfile-lint handles one file per job. For several, use full-scan with dockerfiles: "a,b,c", or include the template once per file with a different job_name.
  • The empty default of tags renders as tags: []. GitLab has no way for an input to omit a keyword, and an empty list is how you say “any runner”. Pipelines accept it; only GitLab's editor JSON schema objects.
